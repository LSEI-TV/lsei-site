Le logiciel **BASKET LIVE** (`D:\BASKET\LOGICIEL-...`) sert des overlays OBS depuis un serveur Node (`serveur-basket.js`, port 3001) qui écrit un fichier unique `basket-data.js` ; les overlays le `fetch`.

**Temps réel (ajouté le 2026-07-04)** : le serveur pousse désormais `{type:'data-changed'}` en **WebSocket** (dépendance `ws`) après chaque `/save-data` ; le client partagé `basket-live.js` appelle `window.OverlayRefresh()` (refresh en place, aussi déclenché à la reconnexion WS) ou fait `location.reload()` en fallback. C'est calqué sur le logiciel sœur **PALET** (`D:\PALET\LOGICIEL PALET`, `server.js`) qui utilise déjà `ws`. L'éditeur (`basket-editeur.html`) n'est **volontairement PAS** câblé à `basket-live.js` (un auto-reload effacerait les saisies en cours).

**Régie (ajoutée le 2026-07-04, comme PALET)** : le serveur a un état `state.activeOverlay` + endpoints `GET/POST /api/overlays`, `/api/overlay/:name`, `/api/overlay-off`, `/api/overlay-toggle/:name`, `/api/state` (registre `OVERLAYS` de 21 overlays dans `serveur-basket.js`). Chaque changement broadcast `{type:'overlay-state', activeOverlay}` en WebSocket. **`basket-master.html`** = LA source OBS unique (1 iframe qui affiche l'overlay actif, fondu). Pilotage : **Stream Deck** (`LIENS-OBS-STREAMDECK.txt`, plugin Web Requests GET) OU **onglet « Régie »** de l'éditeur.

**Ingestion des équipes (ajoutée le 2026-07-04)** : chaque `Equipes/<Team>/` a `logo.png`, `photos/` (identité : `<num>-<Prenom_Nom>-<poste>.png`, staff `staff-<Prenom_Nom>-entraineur[_assistant].jpg`), `liste.txt` (sections `titulaires:`/`remplaçants:`/`entraineur:`/`entraineur adjoint:`, joueurs `num-Nom`), `parcours.txt` (`# Titre` puis `étape | adversaire | score`). L'éditeur : `chargerCompoDepuisDossier` charge les photos puis `appliquerListeEtParcours` applique `liste.txt` (statut titulaire/remplaçant matché **par NOM** via `_normName`, noms sans photo signalés — pas de joueur fantôme) + parse `parcours.txt` dans le global `PC` (sérialisé en `window.parcoursData`). Overlay **`basket-parcours.html?side=dom|vis`** (registré `parcours-dom`/`parcours-vis`). Format documenté dans le README. Bouton **« 🔄 Générer liste.txt (photos) »** (onglet Match, fonction `genererListe(side)`) → `POST /generate-liste {team}` (helper serveur `buildListeContent`) recrée `liste.txt` depuis les photos (5 plus petits n° = titulaires) puis recharge. Les 14 `liste.txt` ont été pré-générées le 2026-07-04 ; ⚠ 9 équipes ont encore les photos placeholder de Fougères (Berck, Fos_sur_Mer, Les-sables, Levallois, Lorient, Orchies, Tarbes, Toulouse, Tours) — à régénérer quand les vraies photos seront en place. Réelles : Fougères, Boulogne-sur-Mer, Le-Havre, Mulhouse, Loon_Plage.

**Chargement équipe « 1 clic » + mémoire sigle/couleur (ajouté le 2026-07-10)** : bouton **« ⚡ Charger l'équipe (tout) »** par côté (onglet Match) → `ouvrirChargerEquipe(side)` ouvre le sélecteur d'équipes en mode `full` → `chargerEquipeComplete(idx)` remplit d'un coup nom+logo+sigle+couleur+nomCourt+effectif+parcours. Nouvelle convention : `Equipes/<Team>/infos.txt` (`sigle:`/`couleur:`/`nomCourt:`) mémorise sigle+couleur par équipe. Écrit via **`POST /save-team-infos {team,sigle,couleur,nomCourt}`** (bouton « 💾 Mémoriser sigle + couleur »), relu en statique (`/Equipes/<Team>/infos.txt`, `parseInfos`). Si pas d'`infos.txt`, sigle auto-proposé par `sigleFromName` (initiales multi-mots → PFB, sinon 3 lettres → MUL). L'ancien « 📂 Choisir le logo seul » reste (mode `match`, nom+logo uniquement). `_chooseMode` = `match`|`full`|`classement` pilote le dispatch de `renderChoixLogo`.

**Onglet Score (ajouté le 2026-07-06)** : saisie MANUELLE du score (table de marque, pas de scoreur auto). Onglet éditeur `panel-score` (avant Régie) : total dom/vis + boutons ±1/+2/+3 + période (Q1-Q4/OT/MT/FIN). Écrit `MD.domicile.total`/`MD.visiteur.total`/`MD.periode`, auto-save débouncé 300 ms (`_scSave`) → overlay live. Overlay **`basket-score.html`** = bandeau score en haut-centre (registré `score`, zone `incrust`). ⚠ chaque save crée un backup → churn possible pendant un match.

**Régie « solo » (pensée pour un opérateur seul, PAS de scoreur/score en direct)** : chaque overlay du registre `OVERLAYS` a un champ `zone` = `moment` (plein écran), `incrust` (bandeau sur caméra) ou `plus` (stats, secondaire). L'onglet Régie affiche 3 zones + un bandeau « 🔴 À L'ANTENNE » + un gros bouton « 🎥 RETOUR CAMÉRA » (= `/api/overlay-off`). Surlignage de l'actif via un WS dédié qui ne recharge JAMAIS l'éditeur. Ordre des onglets éditeur = flux réel : Match → Compositions → Commentateurs/Arbitres/Invités/Partenaires → Affiche → Stats/Classement → Régie. ⚠ `TAB_NAMES` DOIT rester dans le même ordre que les boutons `.tab` (switchTab mappe par index).

**⚠ Dérive doc/code à connaître** : le `README.md` du basket décrit une archi qui n'existe pas (dossier `partials/`, SSE `/events`, endpoints `/backups`·`/restore-backup`·`/data-version`, conflit 409). Le code réel est monolithique (chaque HTML autonome). La suite de tests Playwright (`tests/`) est aussi désynchronisée (teste `/list-teams` inexistant, SSE, backups, panneau debug ; chromium pas installé) → `npm test` échoue. À réaligner avant de s'y fier. Voir [[basket-live-todo]].
